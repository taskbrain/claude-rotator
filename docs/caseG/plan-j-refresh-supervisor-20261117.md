# 差し替え方式：送信側口座 j の資格更新方針と自動更新の仕組み（2026-11-17 JST）

公開用の文書として、手元のパス・メールアドレス・Keychain 項目名・内部の管理番号は書かない。詳細な実機記録は手元の記録ファイルにある。

## 1. 結論

- J2（11/13 決定「期限切れ後に公式 `claude auth status` で更新する」）を、**B → A → C の順の方針**に置き換える（坂根さん決定、2026-11-17）。
  - **B（常用）**：j の設定フォルダで、プロキシなし・質問なしの公式 Claude Code を起動したままにし、公式クライアント自身の自動更新に任せる。
  - **A（予備）**：B で更新されないまま期限を過ぎたときだけ、j の設定フォルダで公式 `claude -p` を 1 文だけ送る（ツールなし・MCP なし・空の作業フォルダ）。既定は無効。
  - **C（最後）**：A も効かない・使えないときは、坂根さんに通知し、坂根さんが公式 `/login` を行う。自動化しない。
- Rotator も差し替えプロキシも、資格を自分で更新しない。トークンの値を読まない・書かない・記録しない。
- この順を実装する「更新監督（refresh supervisor）」を追加する。既定は dry-run（判定を表示するだけ）。常駐化（launchd 等）は今回入れない。

## 4. 更新監督の設計

### 4.1 役割

送信側口座ごとに、次の 3 つだけを行う。

1. **観測**：資格の更新時刻（Keychain の属性 mdat。値は復号しない）、差し替えサーバーの記録にある `credential_expired`（理由コードだけ）、常駐の公式 Claude Code が生きているか。
2. **判定**：B → A → C の方針で、次の行動を 1 つ決める。
3. **行動**（`--apply` のときだけ）：B の常駐起動、A の 1 回実行、C の通知。既定の dry-run では判定を表示するだけ。

### 4.2 状態と判定

| 状態 | 条件 | 行動 |
|---|---|---|
| fresh | mdat の経過 < `staleAfterMs`（既定 9 時間 = 想定周期 8 時間 + 余裕 1 時間）かつ 失効記録なし | なし |
| resident_missing | 常駐が無い | B：常駐を起動（`--apply` 時）。他の Claude Code がそのフォルダを使っている、または判定不能なら起動せず通知 |
| stale | mdat の経過 ≥ `staleAfterMs`、または mdat 以後に `credential_expired` を観測 | 警告を記録・通知。A が有効で条件を満たせば A へ。満たさなければ C |
| fallback_a | A 有効・常駐以外の利用者なし・前回 A から `fallbackA.minIntervalMs`（既定 6 時間）以上・当日の回数上限内 | A を 1 回。終了後に mdat の前進を確認。進まなければ C |
| login_required | A が無効・失敗・上限到達、または mdat 判定不能 | C：坂根さんへ通知（同じ内容は `notifyDedupeMs` の間 1 回だけ） |

- `unknown`（Keychain 属性が読めない、項目が 0 件または複数）では、自動の行動をせず C の通知にする。
- 常駐が生きていて mdat の経過が `staleAfterMs` 未満なら、失効記録があっても何もしない（`resident_refresh_pending`）。常駐は期限付近で更新するため（E4）、その隙間で A を並行に走らせない。
- 常駐の生存・他の利用者・失効記録の読取のどれかが判定不能なら、B も A も自動では行わず通知する（`resident_unknown`、`other_users_unknown`、`expiry_events_unreadable`）。
- 起動したが確認できなかった常駐は記録し、それが残る間は再起動しない（`resident_unverified`）。監督はプロセスを止めない。
- 状態ファイルの不正は初期化せず、その口座の自動行動を止めて通知する（`refresh_state_invalid`）。
- `--apply` は状態フォルダのロックファイル（排他作成）を取ってから動く。取れなければ何もしない（`refresh_supervisor_locked`）。古いロックは自動で消さない。
- 連続再試行はしない。A は既定で無効（`fallbackA.enabled=false`）で、坂根さんの承認後に設定で有効にする。
- 常駐の生存確認で `ps` が失敗した（終了コード 1 でも診断の出力がある、または打ち切られた）ときは「不在」とみなさず判定不能として扱い、常駐の記録を残して起動しない。診断の出力は保存・表示しない。
- 常駐を起動する前に「起動中（pid 未確定）」の記録を状態ファイルへ確実に書き、書けなければ起動しない。pid 未確定の記録が残っている間は自動で消さず起動もしない（人が確かめて直す）。起動・A の実行の後に状態を書けなかったときはロックを残して終了し、人が確かめるまで次の実行を止める。
- 起動中の公式クライアントは設定フォルダのファイルを開いたままにしないことがある（実機 2026-11-18）。そのため sessions/<pid>.json の名前と ps で検出し、期限内なら external_client_present として何もしない。
- sessions/<pid>.json の pid が動いていても公式クライアントと識別できなければ判定不能（通知のみ）とし、名前の作成時刻より 120 秒を超えて後に始まったプロセスは pid の再利用とみなして古い名前として除く。範囲外の pid（2〜2^31-1 の外。11 桁以上を含む）は名前の形にかかわらず無視し、対象の pid が 64 個を超えれば判定不能とする（1 つのクライアントが .json と .key の 2 つの名前を持つので、名前の数ではなく pid の数で数える）。lsof で見つかった pid に公式クライアントと確かめられないものがあれば、従来どおり通知する。
- 初回確認画面（ブラウザ拡張の確認など）で入力待ちの間、sessions には `<pid>.<64桁の16進>.key` だけがあり `<pid>.json` は無い（実機 2026-11-18。人が操作した後に .json ができた）。そのため .key の名前も .json と同じ確認（ps の存在・名前の作成時刻と開始時刻の差・公式クライアントのコマンド）にかけ、生きていれば起動済みとみなして二重に起動しない。同じ pid の名前が両方あれば ps は 1 回で、作成時刻は遅いほうを使う。pid で始まるがこの 2 つの形に合わない名前は、その pid を ps で確かめ、プロセスが無ければ古い名前として無視し、生きている・判定できなければ判定不能（通知のみ、起動しない。理由に名前・pid は出さない）とする。想定外の名前にも lstat だけで作成時刻を取り、期待形と同じ pid 再利用の確認（開始時刻が作成時刻＋120 秒より後なら古い名前として無視）をかける。lstat が ENOENT の名前は無いものとして扱う。自分自身と記録済みの常駐の pid は、形を見る前に除く。ファイルの中身は開かない。

### 4.3 B：常駐起動の条件

- 公式の実行ファイルを**絶対パス**で起動し、引数は付けない（質問の文字列を渡さない）。シェルの別名（権限確認を省く別名がある）を通さない。
- 環境から認証・接続先の上書きを除く：`ANTHROPIC_*`、`CLAUDE_CODE_OAUTH_TOKEN`、接続方式の切替（`CLAUDE_CODE_USE_BEDROCK` など既存 CLI と同じ一覧）、`HTTP_PROXY`／`HTTPS_PROXY`／`ALL_PROXY`／`NO_PROXY`（大文字・小文字）。`CLAUDE_CONFIG_DIR` だけを j の設定フォルダに設定する。
- 作業フォルダは空の専用フォルダ。空でなければ起動しない。
- 対話の公式クライアントは端末（TTY）が要るので、起動は差し替え可能な launcher で行う。今回の実装は「起動計画（argv・env の差分・cwd）を作る」ところまでと、注入された launcher を呼ぶところまで。実機での常駐起動は、坂根さんの承認後の試験で行う。
- 起動後の初回画面（テーマ選択・注意事項・フォルダの信頼確認）は、人が一度だけ進める前提。監督は画面へ入力しない。
- launcher の実装（設定 `refreshSupervisor.launcher` に `{ kind: "orca", orcaBin, worktree, title }` があるときだけ。**実機未検証**）：
  - `--apply` で start_resident のときだけ、`<orcaBin> terminal create --worktree <worktree> --title <title> --command <文字列> --json` をシェルなしで 1 回呼び、Orca の端末で起動する（`--focus` なし）。
  - 端末へ渡す文字列：`cd '<workDir>' && exec /usr/bin/env -i HOME="$HOME" USER="$USER" LOGNAME="$LOGNAME" SHELL="$SHELL" TERM="$TERM" LANG=en_US.UTF-8 TMPDIR="$TMPDIR" PATH=/usr/bin:/bin:/usr/sbin:/sbin CLAUDE_CONFIG_DIR='<configDir>' '<claudeBin>'`。端末の環境は監督の環境と別なので、除去リストではなく env -i と許可リストで、`ANTHROPIC_*`・`CLAUDE_CODE_*`・プロキシなどをすべて落とす。単一引用符を含むパスは設定の検証で拒否する。orca CLI 自身へは HOME・USER・LOGNAME・PATH・TMPDIR・LANG だけを渡す。
  - 端末のログインシェルが zsh/bash で、rc に対話が無いことが前提（実機で確認）。
  - processId は端末ごとの /usr/bin/login（実機 2026-11-18 の観測）。そうでなければ確定しない。
  - PID の特定：出力の `result.terminal.processId` から、`pgrep -P` で子孫をたどり（その pid 自身を含む）、`ps` の command が claudeBin と一致し、開始時刻が orca を呼ぶ直前の 2 秒前以降のもの（それより前に始まったものは別のプロセスとして数えない）が、最大 30 秒（1 秒ごと。期限は探索の途中でも確かめ、各 pgrep・ps の timeout を残り時間で抑える）の間にちょうど 1 つ見つかればその pid を常駐とする。見つからない・複数・開始時刻が読めない・観測できないときは、端末の pid を人が確かめるまで消えない未確認の記録（`manual: true`）に残す。記録した pid が端末の親で、子の claude が残っていることがあるので、ps で不在になっても自動では消さない。他のプロセスの環境は読まない。
  - 監督は端末へ入力・送信せず、端末を閉じず、プロセスを止めない。端末の handle は報告にも状態ファイルにも出さない。

### 4.4 A：1 回実行の条件

- `claude -p '<固定の短い 1 文>' --tools "" --strict-mcp-config` に、権限確認を出さないための公式オプションを加える。使うオプションは実行ファイルの `--help` に実在するものだけにする（存在しないものは使わない）。
- 環境・実行ファイル・作業フォルダは B と同じ条件。上限時間で打ち切り、出力本文は保存しない（終了コードと出力の長さだけ記録）。
- 実行後、mdat が進み、同じ 1 件の項目であることを確かめる。進まなければ C。

### 4.5 C：通知

- 既存の通知（macOS 通知）を使う。本文は「送信側口座 <id> の資格が更新されていません。公式の `/login` をその設定フォルダで行ってください」程度で、秘密・メールアドレスを含めない。
- 監督自身は `/login` を実行しない・ブラウザを操作しない。

### 4.6 記録

- 状態ファイル（0600、原子的書込）に、最後に見た mdat、最後の行動、A の試行時刻と回数、通知時刻を保存する。
- 秘密値・環境変数の値・Claude の出力本文は記録しない。

### 4.7 CLI

```
claude-rotator credential-swap refresh-supervisor --config <path> [--apply]
```

- 既定は 1 回だけ判定して JSON で表示し、終了する（dry-run）。
- `--apply` でも、常駐化（launchd 登録）はしない。

### 4.8 しないこと

- トークン値の読取（`security ... -w`／`-g`、`dump-keychain -d`）、OAuth の自前更新、資格の書き戻し。
- 公式クライアント以外のクライアントを名乗ること、利用上限の回避。
- `/login`・`/logout` の自動実行、claude.ai の設定変更。
- 本番の旧プロキシ（37891）や既存の常駐・設定への変更。

## 5. 規約上の要確認

関係する原文（Consumer Terms §3「Use of our Services」の禁止事項 7、2026-11-17 確認、Effective Oct 8, 2025）：

> Except when you are accessing our Services via an Anthropic API Key or where we otherwise explicitly permit it, to access the Services through automated or non-human means, whether through a bot, script, or otherwise.

公式の Claude Code が自動更新すること自体は公式文書に書かれているが、監督が「更新のためだけに」起動・送信することが「otherwise explicitly permit」に入るかは、文書からは判断できない。

- **要確認 1：更新だけを目的とした、公式クライアントの定期・自動の起動（B）** — 公式の認証案内は公式クライアントによる自動更新を説明しているが（https://code.claude.com/docs/en/authentication）、更新を保つためだけに監督が公式クライアントを起動・常駐させる運用を、Consumer Terms の自動・非人間的なアクセスに関する定め（https://www.anthropic.com/legal/consumer-terms）がどう扱うかは、原文の確認と坂根さんの判断が要る。
- **要確認 2：更新だけを目的とした定期的な `claude -p` の送信（A）** — 推論を 1 回使う。同上の規約の自動化・利用量の扱いに当たるかは要確認。坂根さんは「個人利用なら問題ない」と Anthropic から聞いたとしているが、その出典は未確認。
- C（坂根さんによる公式 `/login`）は公式の手順どおりで、自動化しない。
