### 2.1 503 の理由（推測）

- **事実**: 試作の `credential_unavailable` は「Keychain の読み取り失敗・中身の取り出し失敗・期限が余裕（5分）以内」をまとめた理由。プロキシは更新も書き込みもしない。
- **事実**: 成功（10:59）も失敗（11:55）も、mdat は 03:13:00 のまま。当時の develop@ の login expires は 11/16 16:04。
- **推測**: アクセストークンの期限切れ。03:13 から 7時間46分後は成功、8時間42分後は失敗なので、**アクセストークンの寿命は約8時間**と見るのが整合する。セッション（ログイン）の期限切れとは整合しにくい。503 の原因を期限切れと断定はしない（読み取り失敗など、包括理由の他の枝も残る）。
- **事実**: 持ち主の Claude Code（PID <pid>）は開いたまま待機していたが、e694e038 の mdat は 11/10 03:13:00 から 11/11 15:13:04 まで約36時間動かなかった。
- **推測**: 上記の寿命約8時間を仮に置くと、期限が切れてから次の更新まで約27時間空いた計算になる。これは観測ではなく逆算である。
- **事実から言えること**: **待機中の公式クライアントが、期限の前に必ず更新してくれるとは言えない。**
- **事実（T4 の参考）**: 11/11 の再試験で、表示用 cfg14 の Keychain 項目 `…-7b5bcb04` の mdat が、試験セッション起動時の POST と同じ 15:34:38 に進んだ（実施記録 226行。開いていたのは試験タブで、プロキシの読取対象外）。
- **推測**: 公式クライアントを短時間起動すると、起動時に更新が書かれることがある。1回の観測であり、T4 で確かめる。

### 2.2 1回の質問で要求が2件になる

- **事実**: 段2 と 11/11 の再試験で、質問1回に対して `POST /v1/messages` が2件記録された回がある。待機中にも自動 recap の `POST` が1件あった。
- 計画への影響: 差し替えの数を「質問の数」で数えない。口座の消費の見積もりにも入れる。

### 2.3 起動直後の 429

- **事実**: 段1・段2・11/11 とも、起動直後の `POST /v1/messages` が 429 を返し、その後の質問は 2xx。セッションは止まらなかった。
- 推測: 起動時の補助の要求で、本番の振り分けとは関係が薄い。本番に入れるときは 429 を口座の使い切りと誤判定しない（§5 の S1 の試験に入れる）。起動直後の 429 と、差し替え先 j が本当に使い切った 429 との見分け方（経過時間・ヘッダーなど）は**未検証**。S1 の設計で根拠を書く。書けなければ判断点に出す。本当の使い切り 429 のときは、その口座を候補から外し、同じセッションを維持したまま別の差し替え先へ切り替える（切替試験は S1）。

### 2.4 計上先は断定していない

- **事実（11/11、`claude-rotator status` の読み取り）**: fde@ は週20%・Fable 3% のまま、requests 58882→58979（+97。同じ時刻の本番 Events に fde@ への要求があり整合）。develop@ は週18%・Fable 3%・requests 69159 のまま。
- requests は本番 Rotator の通算で、試験プロキシ（37991）経由は含まれない。週％は丸めのため小さな要求では動かないことがある。
- **事実**: T3 の時間帯に、本番が試験の表示用口座（fde@）や、別回では差し替え先（develop@）へ要求を送っていた記録がある（実施記録 119行・195行・224行）。どの回も「本番が試験口座を使っていない」という条件は緩めて実施している。
- **言えること**: 上流へ送った認証は差し替え先（設定上 develop@）だった（ログの真偽値）。**サーバー側でどの口座に計上されたかは未確認**（claude.ai の使用量画面は見ていない）。

## 3. プロキシが認証を更新しない問題への正規の対応

### 3.1 方針

- **Rotator（新側）は差し替え先のトークンを読むだけにする。自前の OAuth 更新（token 窓口への `refresh_token` の送信）はしない。** 更新は、その口座フォルダの**公式の Claude Code**に任せる。1口座につき、更新するのはその口座フォルダ1か所だけにする（リフレッシュトークンの世代のぶつかりを避ける。`design.md` §4 案C）。
- 自前の OAuth 更新を新側に入れる案は、**規約上「要確認」**（§8.1 の原文。「Claude.ai の認証情報やセッショントークンを集める・保管する・仲介する」ことを許さない文に当たるかが原文からは決まらない）。本計画では採らない。
- なお、いまの本番も自前の更新（`src/oauth.js`）を持っている（**事実・コード**）。新側でこれを使わないことで、旧本番よりも規約上の論点を減らす向きになる（推測）。自動の短時間起動そのものは、別の規約論点になりうる（§8.4）。

### 3.2 期限が近いときの振る舞い（新側のプロキシ）

1. 差し替え先の候補から、アクセストークンの期限が余裕（既定5分）以内の口座を外す。値は読まず、期限の数字だけを内部で比べる。
2. 候補が無ければ**差し替えずに通す**（そのセッション自身のログイン＝表示用口座 k で送る）。そのセッションの Claude Code は自分のログインを自分で更新するので、503 で止めるより安全。T3 の試作は試験のために 503 で止めていたが、本番ではこの「通す」を、次の例外を除き既定にする。
3. **例外（k の残量）**: k の残量が閾値を下回っているときは、通さず、要求を失敗させ、記録を残す。閾値は口座選びと同じ考え方（`design.md` §6 の 97〜98%）を仮置きし、S1 で決める。
4. **記録**: 差し替えたときは口座 j、通したときは口座 k を `usage-events` に書く。欄で区別する（例 `swapped=true/false`）。Claude Token Monitor は実際に上流へ送った口座で集計する。
5. **401 と 403 を分ける。** 401（期限切れの可能性）を k で送り直すのは、要求本文を上流へ送る前に失効が分かった場合に限る（再試行の上限は1回。k の残量例外は適用する）。すでに上流へ送った要求を別の認証で送り直すことはしない。ストリーミング本文を保持できるかどうかは S1 で決める。送り直しそのものが制限の迂回に見える可能性は、403 と同様に残る（推測）。規約上の要確認の点として残す（J1 は問い合わせずに進むと決定。2026-11-11、t96s831）。**403 は通し直さない。** その口座を候補から外し、記録を残して人の判断を待つ。停止の範囲（後続の要求、プロセス再起動のあと、拒否した口座が k と同一のときの「通す」）と解除条件は S1 で書く。中止の条件も「403 は1回で止める」（T3 の手順に戻す）。

### 3.3 休んでいる口座を誰が更新するか（未解決。T4 で決める）

§2.1 のとおり、開いたまま待機している公式クライアントは、観測した約36時間のあいだ mdat を進めなかった。案は次の3つ。どれも**公式の Claude Code にだけ更新させる**。

| 案 | 中身 | 良い点 | 悪い点・未検証 |
|---|---|---|---|
| 保守の短時間起動（推奨候補） | 期限が近い口座について、Rotator がその口座フォルダで公式の Claude Code を短く起動し、更新させて終わらせる（例: `claude auth status`。**これで更新されるかは未検証**） | 常駐が要らない。更新は公式クライアント。起動時に更新が書かれたことと整合する観測が1回ある（§2.1。推測。T4 で確かめる） | どのコマンドで推論を使わずに更新されるかを T4 で確かめる。推論が要るなら、ごく小さな消費が出る。同一フォルダに作業セッションがあるときの協調も未検証。自動起動は §8.4 の要確認 |
| 保守の常駐 | 口座ごとに公式の Claude Code を1本開いたままにする（T3 の 13945 と同じ） | T3 と同じ形 | 待機中は期限前に更新しないことがある（§2.1。**事実**）。16本の常駐が要る |
| 期限が近い口座は使わない | 更新を待たず、期限の口座を候補から外すだけ | 一番簡単 | 口座が順に使えなくなっていく。単独では足りない |

- 既存の `src/native-claude-refresher.js`（公式の `claude auth login --claudeai` を一時フォルダで動かす）は、**新側の口座フォルダには使わない**。一時フォルダでのログインは別の認証を作るので、口座フォルダの認証の持ち主が2つになる（推測。`design.md` §7 の「Claude Code が持つ口座では呼ばない」に合わせる）。

## 4. 16口座の切り替え・Claude Token Monitor との整合

### 4.1 口座の置き方

- 16口座それぞれに口座フォルダ（`CLAUDE_CONFIG_DIR`）を1つ作り、坂根さんが正規の `/login` を1回ずつ行う（試験3・T3 の cfg14・cfg15 と同じ形）。Keychain の項目名は `Claude Code-credentials-<フォルダの sha256 の先頭8桁>` になる（**事実**、`verification-summary.md` §2）。
- 新しいセッションは、口座フォルダ k で起動する。画面の表示は k。推論は Rotator が選んだ口座 j の認証で送る（j＝k のこともある）。
- **S3 以降の k は、その時点で新側へ移した口座に限る。** `claude-rotator launch` は、移していない口座フォルダでの起動を拒否する（S3 の試験）。限らないと、§3.2 の「通す」がまだ旧側にある k で推論し、同じ口座を新旧が同時に使う。
- 通した要求の口座 k は、起動時に登録した口座フォルダとの対応から特定する。トークンが更新されたあとも同じ対応を維持する。特定できない、または不一致のときは通さず拒否する（S1 で確定）。
- 1つの口座フォルダに複数のセッションを起動してよい（同じフォルダのセッションは同じ認証を見る。**事実**）。表示用の k は、使用量の少ない口座に偏らせず、口座ごとに均等に割り振る（表示用のログインが切れると、そのフォルダのセッションは送る前に止まるおそれがあるため。`design.md` §4 案C）。

### 4.2 旧本番と新側で同じ口座を扱うとき

- 旧本番（37891）は口座ごとに**別の**ログイン（Rotator の保管庫の認証）を持ち、自分で更新している。新側は口座フォルダの認証を読む。同じ口座でもログインが別なので、リフレッシュトークンの系統も別になる（推測。同じ口座で複数の端末にログインできるのと同じ扱いと見ている。**未検証**）。
- それでも、移行の最初は `plan.md` のとおり**新側に2口座だけ**移し、その2口座は旧本番の振り分けの候補から外す（本番の設定変更なので判断点 J3）。
- **外す順序（`design.md` §4 案D 第3項に合わせる）**。これは旧本番（37891 / PID <pid>）への変更になる。S1 の「本番の動きは変えない」とは別に、J3 の承認が要る。
  1. 先に、いまの本番コードだけで、下の**止める対象をすべて**止められるかを確かめる。設定の変更だけで登録から外せて、かつ戻せるなら、コード変更は不要かもしれない。できないなら、旧側に口座ごとの禁止フラグを足す小さな PR と、旧プロセスの再起動が要る。再起動は本番配備であり、J3 と別途の導入承認（J7 と同じ重さ）を取る。
     - **止める対象**（**事実・コード**、`src/proxy-server.js`）:
       - (i) 対象口座への**新しい割り当て**。
       - (ii) **既存の Affinity セッション**（その口座にすでに紐づいたセッション）の続きの要求。新しい割り当てだけを止めても、これは残りうる。
       - (iii) **実際に token 窓口を呼ぶ関数 `refreshAndStoreSecret` に至る経路**。`src/` 全体で `refreshAndStoreSecret` を検索した結果、呼び出し元は次の2か所だけだった（定義は `src/proxy-server.js` 3795行。**事実・コード**、確認日 2026-11-11、関数名とファイル・行だけを根拠にし、値は読んでいない）。
         - `src/proxy-server.js` 3784行: `refreshSecretIfExpiring` の中（期限が近いときの更新）。`refreshSecretIfExpiring` を呼ぶのは次の4経路: 使用量取得の `refreshAccountUsage`（2809行。定期の `refreshAllOnce` から）、リクエスト途中の `forwardWithRotation`（3196行）・`forwardQuotaRecovery`（3593行）・`forwardCurrentUnavailableAccount`（3743行）。
         - `src/proxy-server.js` 3315行: `forwardWithRotation` の中で、上流が 401 を返したとき（`retryAfterRefresh`、3310–3321行）に `refreshSecretIfExpiring` を通さず**直接**呼ぶ経路。
         - したがって止める経路は5つ: (iii-a) 使用量取得、(iii-b) `forwardWithRotation` の期限前更新、(iii-c) `forwardWithRotation` の 401 のときの直接更新、(iii-d) `forwardQuotaRecovery`、(iii-e) `forwardCurrentUnavailableAccount`。
       - `refreshAndStoreSecret` を通らずに token 窓口の更新関数（`tokenRefresher` / `src/oauth.js` の `refreshAccessToken`）を使う箇所もある。`src/cli.js` の doctor（`inspectDoctorWarnings` から `refreshDoctorSecretIfNeeded`・`refreshDoctorSecret`、1235・1250・1289–1309行）が `tokenRefresher` を直接呼ぶ（**事実・コード**）。これは常駐のプロキシではなく手で流すコマンドだが、対象口座で doctor を流さないことを除外の手順に入れる。`src/native-claude-refresher.js` と、ほかに `refreshAccessToken` を呼びうる経路を全部洗い出したかは**未検証**（S3 の前にコードで確かめる）。
     - 起動時の `reconcilePersistedRefreshIntents` は、保存済みの認証の状態を照合する処理で、`refreshSecretIfExpiring` を直接は呼ばない（**事実・コード**）。ここから認証更新に至る道があるかは、S3 の前にコードで確かめる（**未検証**）。
  2. 承認した手段で、(i) と (iii) の5経路（(iii-a)〜(iii-e)）を先に禁止する。対象口座で `src/cli.js` の doctor を流さない。
  3. (ii) の既存セッションを扱う。手順は次のどちらかを J3 で選ぶ。
     - **付け替える**: 紐づいたセッションを旧側の別の口座へ付け替える（プロンプトキャッシュは作り直しになる。許容済み）。いまのコードで口座ごとの付け替えができるかは、手順1でコードを確かめる（**未検証**）。
     - **自然に終わるのを待つ**: 紐づいたセッションが0件になるまで、その口座を新側へ移さない。0件は Session Affinity の口座ごとの内訳で確かめる。
  4. 進行中の要求と進行中の更新が終わるのを待つ。
  5. そのうえで候補から外し、新側での利用を始める。
  6. 除外のあと、**経路ごとに**止まっていることを S3 の除外試験で確かめる（§7 S3 合格条件⑤）。
- 瞬間的な確認だけで除外すると、確認の直後に旧側が再割り当て・既存セッションの続き・リクエスト途中の更新・定期更新を始める穴が残る。
- 「旧本番の設定は変えない」は、J3 で承認した除外（と、必要な場合の旧側コード変更・再起動）を除く、という意味に限る。

### 4.3 口座選びと使用量の表示（Claude Token Monitor）

- **事実**: Claude Token Monitor は、Rotator の `/internal/status` を読み、`usage-events.jsonl` を取り込んで口座ごとの 5h/7d 利用率とコストを表示する（`~/develop/project/ClaudeTokenMonitor` の README）。既定の保存先は `src/paths.js` のとおり、ホーム配下の共通ディレクトリである（**事実・コード**）。
- **新側は旧本番と状態ファイルを共有しない。** `design.md` §4 案D: 「新方式は別ポート・別の台帳で起動し、いまの `runtime-state.json` を共有しない」。既定の保存先のまま別プロセスを起動すると、互いのスナップショットを上書きし、旧側の割り当て・使用量・復旧状態を失う可能性がある（`src/proxy-server.js` の `persistState` は全体スナップショットを書く。**事実・コード**）。
- 第1版で書いていた「同じ口座の台帳に載せる」は、この上書きの危険を定義しないまま残していたため撤回する。意図（同じ口座を新旧が別々に数え、使い切りを見落とすのを避ける）は、次の集約で満たす。
- **書き込みの責任**: 旧側は今の保存先だけを書く。新側は別の設定ディレクトリ・別の `runtime-state.json`・別の `usage-events.jsonl` だけを書く。ロックは各ファイル系の中で完結させる。
- **読み取りの集約**:
  - **足してよいもの**: リクエスト単位の `usage-events`（トークン数・費用）。同じ要求の二重記録は除いてから足す。
  - **足してはいけないもの**: サーバーから取る 5h/7d の利用率。これは口座全体の観測なので、新旧で足すと二重に数える。口座ごと・対象期間ごとに、有効な観測を**1つだけ**選ぶ（移管済み口座は新側が取得する、など）。観測時刻・リセット・欠測を考慮する。
  - 新側が使用量 API を呼ぶ場合も、トークンは更新しない（期限が近い口座は呼ぶ前に外す）。呼ぶかどうかは S2 で決める。
  - 新側の選択は、移管済み口座については旧側利用が0である前提を、除外試験で支える。重なって書き込む期間は作らない。移管・復帰を含む集約は S2 の試験にする。
- 使用量の記録は、**実際に上流へ送った認証の口座**で書く（差し替えなら j、通したなら k。§3.2）。表示用の口座 k は別の欄（例 `displayAccountId`）に入れる。
- `/status`・`/usage` の画面は k を示し続ける（案C の間は許容済み）。**口座の使い方の正本は、集約した Rotator の記録と Token Monitor**であり、`/status`・`/usage` を計上の証拠にしない。
- 計上先そのもの（サーバー側の台帳）は未確認（§2.4）。S0 の試験 T5 で、claude.ai の使用量画面を人が見て確かめる。確かめられるまで、Token Monitor の表示は「Rotator が送った口座」として扱う。
- Token Monitor が新側のポート／ファイルを取り込めていることは、旧側の数字との突き合わせとは独立に確かめる（S3 の合格条件④）。

### S1 PR1: 新しいモードを既定オフで追加（本番の動きは変えない）

- 中身: 通信の分類（推論の `POST /v1/messages` とそれ以外）、差し替え先の認証の読み取り（service・acct・Keychain を限定し、1件だけを確かめる。refresh token を含む全体を内部で読むことがあるが、外へ出さない）、期限が近いときは差し替えずに通す（§3.2）、401/403 の分岐、記録には値を入れない（method・path・status・時間・真偽値・口座 ID だけ）、使用量の記録は実際の上流口座で書き表示口座 k を別欄に置く（§3.2・§4.3）。呼び出し元については、試作の形式確認（Bearer の形・Host・Origin の有無）と、J6 が求める呼び出し元の認証を区別して設計する（§9）。
- 試験（偽の上流・別ポート。実サービスへ届かせない。新側は別の状態ディレクトリ）:
  - 差し替えるのは `POST /v1/messages` だけ
  - 期限が近いと差し替えずに通し、`usage-events` は k で記録される
  - k の残量が閾値未満なら通さない
  - 401 では候補から外して1回だけ通す。403 では通し直さず、口座を外して止める
  - 起動直後の 429 で口座を使い切り扱いにしない。本当の使い切り 429 との見分け方を試験に書く
  - **同じ起動中セッション**で差し替え先を別口座へ変え、応答の完了と使用量の帰属を確認してから戻す（大規模同時試験とは分ける。T3 は再起動なしの切替を検証していない。出典: `test-T3-plan.md` §11、`test-T3-run-plan.md` §4）
  - 記録に token・ヘッダーの値が出ない
  - 既定の保存先を書いていないこと、旧側の状態ファイルが変わらないこと
  - 呼び出し元の認証を入れる（**決定（2026-11-11、t96s831）: J6**）。未許可の呼び出し（形式確認だけを満たす任意の Bearer を含む）を拒否する試験を必須にする。共有秘密の渡し方（環境変数の名前や BASE_URL の path など）を S1 で設計し、`ps` やログに値が出ないこと、§5 の除外リストとの例外を明記する
  - フック発火・deny・CLAUDE.md・ツール実行（git status など）
  - 親環境または取り込み設定に `CLAUDE_LOGIN_OVERRIDE_ENV_VARS` があるとき、値を出さずに起動を拒否（または除去したことを確かめる）
  - k を特定できない要求は通さない
  - 同じポートでプロセスを再起動したあと、既存の接続の扱い（送り続けられる／明確に失敗する）が文書どおりであること

### S2 PR2: 口座フォルダの台帳と更新の持ち主
