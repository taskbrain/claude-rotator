## 0. 結論（先に）

- 確かめること（計画 §7 S0 の T4）:
  1. 口座フォルダで公式の Claude Code を**どう起動すれば、推論を使わずに**アクセストークンが更新されるか（まず `claude auth status`）。
  2. アクセストークンの寿命（約8時間という推測。計画 §2.1）。
  3. 同じフォルダに作業セッションが開いているときの協調（2つが同じ Keychain 項目を書くときに、どちらかが壊れないか）。
- 進め方は3段。
  - **段A（推論なしの更新）**: 期限が近い（または切れた）状態の口座フォルダで、推論をしない公式のコマンドを1つずつ流し、期限の数字が前に進むかを見る。推論の有無は、T3 の試作プロキシ（passthrough）の記録で `POST /v1/messages` が0件かで見る。

  - **段C（協調）**: 別の時間帯に行う。結果は J2 と S2 の設計の材料にする。T4 の合格には要らないが、行わなければ「協調は未確認」と書く。
- どの候補でも推論なしで更新できなければ、**「ごく小さな推論で更新する」を判断点 J2 として坂根さんに出す**（T4 の中では推論による更新を行わない。§7）。
- 坂根さんの作業: 段B の起動と画面の確認、Keychain の確認画面が出たときの「許可」（「常に許可」は押さない）、必要な場合だけ `/login`。約20分。全体の作業は約60分（ほかに、期限が近くなるまで最長約8時間置いておく待ちと、期限補助・T4 確認の再レビューが要る。§11）。

### 2.2 「期限が近い状態」の作り方

- 対象フォルダを開いているプロセスが無い状態で、最後の更新（Keychain 項目の mdat）から時間を置く。寿命が約8時間なら、mdat から7時間半ほどで余裕5分を切る見込み（**推測**）。
- 期限補助で「余裕を切っている」が真になってから段A を始める。期限が切れたあとから始めてもよい。どちらから始めたかを記録する（切れる前と切れたあとで振る舞いが違う可能性がある）。
- 期限補助が「余裕を切っていない」と出ているうちは段A を始めない。更新が要らない状態でコマンドを流しても、更新の有無は判定できない。

### 2.3 推論の有無の見方と、その限界

- 段A のコマンドは `ANTHROPIC_BASE_URL=http://127.0.0.1:37991` を付けて流し、試作プロキシの記録で `POST /v1/messages` が0件なら「推論を使っていない」とする。
- 限界: BASE_URL を付けたときと付けないときで、Claude Code の振る舞いが違う可能性がある（**未検証**）。T4 で合格とするのは、BASE_URL を付けた形だけにする。本番の保守起動も、新側のプロキシの BASE_URL を付けた同じ形で動かす前提で記録する。
- token 窓口への更新の通信が BASE_URL を通るかは分からない（**未検証**）。`/v1/messages` 以外に記録されたパスは、パス名だけを記録する。

### 段C 協調（別の時間帯。段A で更新できる形が見つかったときだけ）

- 目的: 同じフォルダに作業セッションが開いているときに、段A の形で更新させても、作業セッションと更新の起動のどちらも壊れないかを見る。
- 対象は段A と同じフォルダ（cfg14 など）。**cfg15 の 13945 は使わない**（既存のプロセスに影響を与えないため）。
- 手順:
  1. 段A の更新から、再び期限の余裕を切るまで置く（§2.2）。
  2. その少し前に、坂根さんが対象フォルダで作業セッション役のタブ「T4-段C-作業」を BASE_URL 付き（37991 の passthrough）で起動し、質問はせずに待つ。起動直後の `POST /v1/messages` は記録する（推論が少し出る。段C の目的の外として記録する）。
  3. 期限補助で余裕を切ったことを確かめたら、私たちが段A の形を1回流す。
  4. 坂根さんが作業タブで質問を1回し、答えが返るか、Not logged in・Login expired・`/login` が出ないかを見る。
  5. 期限補助・mdat・`lsof` で、どちらが更新したか（作業タブが先に更新したか、段A の形が更新したか）を記録する。
- 作業タブが自分で先に更新した場合は、それも協調の観測として記録する（その場合、段A の形が書いたときのぶつかりは確かめられていないので、「ぶつかりは未確認」と書く）。

## 6. 判定

| 項目 | 合格 | 不合格 | 未確認 |
|---|---|---|---|
| 推論なしの更新 | 余裕を切った（または切れた）状態から始め、段A のある形のあとで期限が前へ進んだ（差が正）。同じ回の `POST /v1/messages` が0件。対象フォルダを開いたプロセスが試験のコマンドだけで、mdat の進みがそのコマンドの時刻と合う。段B で差し替えの 2xx が出た | 全部の候補で、期限が進まなかった（§7 の J2 の判断点へ） | 始めたときに余裕を切っていなかった。他のプロセスが開いていた。期限補助が読めなかった。段B を行えなかった |
| 寿命 | 更新の直後の残り時間（10分単位）を記録できた。約8時間かどうかを書く（違えば計画 §2.1 の推測を直す材料にする） | — | 段A で更新できなかった |
| 協調 | 作業タブと段A の形のどちらも、エラー・Not logged in・Login expired にならず、期限が前へ進んだ | どちらかが失敗した、または `/login` を求められた | 段C を行っていない。作業タブが先に更新して、ぶつかりの場面が起きなかった |

- **mdat が進んだだけでは合格にしない**（期限の差が正であることが要る。計画 §7 S0）。
- 段B の差し替えは小さな推論を使うが、これは合格の確認のためで、更新の手段ではない。更新の手段に推論が要るかの判定には数えない。

## 7. 推論なしで更新できなかったとき（J2 の判断点の出し方）

T4 の中では推論による更新を行わない。結果を添えて、坂根さんに次の形で出す（計画 §10 の J2）。

1. 何を決めるか: 休んでいる口座の更新に、ごく小さな推論を使ってよいか。
2. なぜ: 推論なしの形では期限が進まなかった（段A の結果を添える）。決めないと、差し替え先が順に期限切れになり、計画 §3.2 の「通す」に落ちる要求が増える。
3. 選択肢:
   - ア: 期限が近い口座について、口座フォルダで公式の Claude Code をごく小さな推論つきで短時間起動する（例: 対話で起動してすぐ `/exit`、または短い質問1回）。口座ごとに小さな消費が出る。自動起動が Consumer Terms §3-7 に当たるかは要確認のまま（計画 §8.4）。
   - イ: 口座ごとに公式の Claude Code を常駐させる。待機中は期限の前に更新しないことがある（計画 §2.1、**事実**）。
   - ウ: 期限の近い口座は使わない（計画 §3.3）。単独では足りない。
4. 推奨: T4 の結果を見てから書く。アを推奨するなら、消費の見積もり（1回あたりの要求件数）を T4 の別回で測るよう、判断点に添える。

## 8. 中止の条件（どれかで止める）

## 10. 記録の残し方

- 実施記録を新しいファイル（例 `records/caseG-T4-run-<日付>.md`）に書く。commit するかは別に決める。公開リポジトリの追跡下なので、commit・push の前に、口座のメール前半・PID・手元のパスなどの公開可否を差分で確かめる。
- 書くもの: 時刻（JST）、段と番号、実行したコマンドの形（値は無い）、終了コード、期限補助の出力（真偽・差の分・丸めた残り時間）、mdat、`lsof`・`pgrep` の結果（PID とコマンド名）、プロキシの記録の件数とパス名、Keychain の確認画面の有無・項目名・時刻、坂根さんの画面の観察。
