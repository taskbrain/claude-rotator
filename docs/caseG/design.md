## 1. 方針（坂根さんの指示、2026-11-03）

1. `--resume` で引き継ぐ方式はとらない。起動中のセッションを再起動せず、いまの Rotator のように**裏で口座を切り替える**。作り直してよいのはプロンプトキャッシュだけ。
2. 画面は本来のサブスクリプション表示（API Usage Billing を出さない）。`/feedback` が送れること。
3. 規約: 同じ PC の中で自分の口座のログインし直しを簡易にしているだけなので問題ない、というのが**坂根さんの解釈**（https://www.anthropic.com/legal/consumer-terms ）。設計はこの解釈を前提にする。
4. 規模: 口座16個、同時セッション約100。本番の Rotator（127.0.0.1:37891 のプロキシ方式）を止めずに移す。

これにより、以前の Page にあった「口座ごとのフォルダで起動し直し、`--resume` で引き継ぐ」案は**取り下げ**。

## 4. 各案のくわしい中身

### 案A（最終形の候補）
- 口座ごとに「いまの保存先・持ち主のレーン・状態・管理用の世代番号」を記録する（世代番号は Rotator 側の番号で、サーバーのトークン世代そのものではない）。
- 動いている口座の正本はレーンの Keychain 項目と `oauthAccount`。休んでいる口座は保護した保管場所に置き、別の Claude Code が更新しない状態にする。
- 切り替えの手順: 予約 → 受付を待たせる → 進行中の作業が終わるのを待つ → 最新を取り込み → 移す → 照合 → 追従を確認 → 再開。
- 途中で落ちても、2か所を両方「使える」状態に戻さない。
- Keychain と JSON（`oauthAccount`）は別の保存先なので、書く順番や rename だけでは全員に同時に切り替わらない。
- **成り立つ最大の条件**: Claude Code がトークンを更新する直前の再読み込み・排他と、外からの切り替えが協調できること。プロキシで通信を止めても、裏で動く更新や古いメモリの状態は止められない。確認できなければ A を本番に上げない。
- 割り当ての案: **8レーン × 12〜13セッション、各レーン専用に2口座**（使う8口座・待機8口座）。1レーンに100セッションは影響が大きすぎ、16レーンに16口座全部を使うと切り替え先の余裕がない。

### 案B
- 元のフォルダから世代 g を渡した後、レーンが g+1 に更新すれば元は古くなる。切り替え直前に取り直しても、その後の同時更新は防げない。
- 元側を更新できなくすれば、実質 A になる。単独では勧めない。正規ログインによる最初の登録の手順だけ流用する。

### 案C（移行・実証の段階）
- `ANTHROPIC_AUTH_TOKEN` を外し、正規ログイン＋`ANTHROPIC_BASE_URL` だけで起動する。
- 推論の要求は、いまの `forwardWithRotation` と Authorization の差し替えを流用する（`src/proxy-server.js` のヘッダー生成は、入ってきた Authorization を消して差し替えている）。
- `/status`・`/usage` はログインしている側の口座を示すはず。実際の口座は Rotator 側の記録で確かめる。画面の表示を計上先の証明にしない。
- 表示用のログインが切れると、プロキシに使える口座があっても Claude Code が送る前に止まるおそれがある。
- `/feedback`: BASE_URL を通るのか、直接送られるのかを先に確かめる。通るなら、feedback は元のログインの Authorization のまま送り、別口座へは差し替えない。成功の基準は「送信成功の表示と受付 ID」。zip の保存は成功に数えない。
- 世代のぶつかりを防ぐ作り: 1口座に正規ログインの保存先を1つだけ持たせ、更新はその保存先の Claude Code に任せる。プロキシは最新のアクセストークンを**読むだけ**で、リフレッシュトークンを別に写さず、自分では更新しない。
- **使っていない口座は誰が更新するか（2回目で確認）**: その口座のフォルダで Claude Code が動いていなければ、誰も更新しない。案は、口座フォルダで保守用の Claude Code を常駐させるか、使う前・定期的に短く起動すること。短く起動するだけで必ず更新されるか、`claude auth status` で更新されるかは**未検証**。
- 割り当ての目安: 100セッションを16口座に 6〜7 ずつ。

### 私たち（Grok Bot）からの補足
- C の「レーン」は、**口座ごとのフォルダそのもの**にするのが素直（試験3と同じ形）。セッションはどこかの口座フォルダ k で起動し、画面は k のサブスク表示になる。k の更新はそのフォルダの Claude Code が受け持つ。プロキシは他の口座のアクセストークンを読んで送り先を変える。こうすると、1口座につき更新の持ち主が1か所という条件を自然に守れる。
- いまの Rotator は Claude Code の Keychain 項目を `security` で読んでいる（`src/claude-credentials.js`）。口座フォルダの項目を読むときに確認画面が出ないかは**試験で確かめる**（10/31 にはコピーした実行ファイルで確認画面が毎回出た）。

### 案D（おすすめ）
1. 本番の 37891 は残す。新方式は別ポート・別の台帳で起動し、いまの `runtime-state.json` を共有しない。
2. 最初は1レーン・2口座（例: 旧側14口座、新側2口座）。同じ口座を新旧の両方が更新しない。
3. 旧側から口座を外すのは、新規割り当て・使用量取得による更新・進行中の更新が残っていないと確かめてから。
4. 新しいセッションは、最終的に A で使うのと同じフォルダで、正規ログイン＋BASE_URL だけで起動する。C の間はプロキシで振り分ける。
5. A の試験に通ったら、そのレーンの送り先をログイン中の口座にそろえ、プロキシは Authorization をそのまま通す。その後、保存先の切り替えを有効にする。
6. 新しい起動と旧セッションの自然終了に合わせて広げる。

## 5. 既存のセッションの扱い（大事な点）

- いま `~/.claude` で動いている約100セッションは、起動時にダミーの `ANTHROPIC_AUTH_TOKEN` を持っている。設定ファイルを直しても、起動中のセッションの認証の仕方が変わるかは**未検証**。フォルダも起動時に決まるので変えられない。
- そのため、**どの案でも、既存のセッションは自然に終わるまで今の方式（裏での口座切り替えは今どおり続く）**、新しく起動したセッションから新方式に入れる。これが Codex と私たちの一致した見方。
- 「いま動いているセッションまで即座に新方式に移す」ことを必須にすると、いまの根拠では設計を決められない。

## 6. 主な危険

| 危険 | 何が起きるか | 対策 |
|---|---|---|
| リフレッシュトークンの世代のぶつかり | 古いメモリや控えから更新し、最新の系統を失う | 口座ごとに更新の持ち主を1つに固定。新旧の境目でも排他 |
| Keychain の ACL と確認画面 | ヘルパーは書けても Claude Code が読めない・保存できず、後で切れる | 通常の実行ファイルで確認。コピーした実行ファイルは使わない |
| USER / acct・HOME | 別の項目を探してログアウト扱い | 起動・確認・子プロセスで統一。USER が無ければ推測で補わず起動を拒否 |
| `oauthAccount` の書き込み競合 | 他のセッションが古い口座情報で上書き | 該当部分だけマージ。共有の排他がなければ競合は残る |
| Claude Code の自動アップデート | ロック・保存形式・キャッシュが変わる | 動いている版を記録し、未検証の版が混ざったら A の新しい切り替えを止める |
| 一斉追従 | 更新の集中、キャッシュの作り直し、新旧口座の混在 | レーン単位で順番に切り替え |
| サブエージェント | 親と別の認証状態で動き続ける、切り替え前の要求が後から送られる | 子のフォルダの引き継ぎ・独立プロセス・背景作業を試験 |
| 97〜98% の切り替え | 既定15分の使用量取得の間に超える | 97% で次の口座を予約、98% で新しい作業を待たせる。応答ヘッダーなども使って早める。値が無いときは 0% とみなさず待つ |

`sessionAffinity.hold()` は HTTP の要求を待たせるだけで、ツール実行を含むターン全体や裏の更新の完了は保証しない（`src/session-affinity.js`）。

## 7. コードの変更場所（Codex の整理）

| 場所 | 方針 |
|---|---|
| `src/proxy-server.js` | C は `forwardWithRotation`・SSE・使用量の観測を流用。推論と補助の通信（feedback など）で認証の方針を分ける |
| `src/session-affinity.js` | C で割り当て・予約を流用。A ではレーン固定が中心になる |
| `src/account-manager.js` | 使用量・候補選びを流用。持ち主・予約・移行中・停止中の除外を追加。97〜98% の厳密な停止は別に要る |
| `src/secret-store.js` | 旧口座はいまの排他と記録を維持。A には移動用の永続状態を設計 |
| `src/native-claude-refresher.js` | 旧 Rotator が持つ口座だけに残す。Claude Code が持つ口座では呼ばない |
| `src/claude-keychain.js` | 名前の計算を流用し、起動時のフォルダ名と実際の項目が一致するか確かめる |
| `src/claude-credentials.js` | いまの Mac の読み取りはサービス名だけで探すので、そのまま使わない。service・acct・保存先を限定する読み取りを足す |
| `src/config.js`・`src/install.js`・`src/cli.js` | 新方式を明示のモードとして足す。全体設定の一括削除を避ける |
| 新規（レーン管理）・README | 口座の予約・持ち主の移しかえ・待機・停止を担当 |

注意（Codex）: いまの「live credential のミラー」と「自動更新」を両方残したまま A/C につながないこと（`src/proxy-server.js` の認証解決とミラーの箇所）。設定の再読み込みで所有方式の変更を 409 で止める処理があるので、設定変更だけの無停止移行は前提にできない。

## 8. 坂根さんに決めてもらうこと

1. **移し方**: 既存のセッションはそのまま残し、新しく起動する分から移す（案D）でよいか。
2. **C の間の表示**: サブスクの表示にはなるが、`/status`・`/usage` の口座と実際に使う口座がずれる期間を許すか。R3 を「API Usage Billing が出なければよい」と読むなら C は候補、「表示と実際の計上先が一致」まで求めるなら C は一時的な段階としてだけ使う。
3. **レーンの数**: A の初期目標を 8レーン・各12〜13セッション・各レーン専用2口座としてよいか。
4. **待ちと閾値**: 97〜98% を目安に、消費の見込みで早めに待たせたり、長い作業の終わりまで切り替えを延ばしたりしてよいか。
5. **A へ進む条件**: R8（世代のぶつかり）を防ぐ方法を確かめられなければ C のままにするか。事故が出なかったことだけを根拠に A へ進めることは勧めない（Codex）。
