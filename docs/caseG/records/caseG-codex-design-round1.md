  ## 3. 案A：共有レーンへ認証情報を「移す」
  最終形として要件に最も近い一方、実装難度とR8の不確実性が最大です。
  • 口座ごとに「現在の保存先・所有レーン・状態・管理世代」を記録します。管理世代はRotator側の番号であり、サーバーのtoken世代を直接表すものではありません。
  • 活動中の正本はレーンのKeychain項目と対応するoauthAccount。休眠口座は保護ストアに保管し、別のClaude Codeが更新する状態にしません。
  • 切替前に活動側の最新状態を再取得し、古い控えを上書き元にしません。休眠口座の復帰時にClaude Codeが自動更新できることも試験対象です。
  • 所有権移動は「予約→受付待機→進行中作業の完了待ち→最新取得→移動→照合→追従確認→再開」とします。
  • 転送途中に二つの保存先へ存在する場合でも、更新できる所有者は一つに限定します。途中でクラッシュした場合は、両方を自動的に活動状態へ戻しません。
  • KeychainとJSONは別ストアです。書込順・再読取・原子的renameだけでは、全読取側に対する一括切替にはなりません。
  最大の成立条件は、Claude Codeのrefresh直前の再読込・排他と、外部切替が協調できることです。
  通常操作のidle確認やプロキシの通信停止だけでは、背景refreshや古いメモリ状態を止められません。協調方法を確認できなければ、本番Aへの昇格を保留します。既存設計の保証境界 (docs/caseG/records/caseG-credential-switch-設計-20261027.md:328)
  割り当て案：8レーン、各12〜13セッション、各レーン専用2口座。
  4レーン×13＋4レーン×12＝100。活動8口座・待機8口座とし、最初は口座の組を固定します。
  1レーン100セッションは停止・追従の影響が大きく、16レーンで16口座全部を活動させると切替先の余裕がありません。
  ## 4. 案B：口座ごとの正規ログインからレーンへ渡す
  正規ログインの維持には有利ですが、「最新を渡す」だけでは世代衝突を解決しません。
  • 元フォルダから世代gを渡した後、レーンがg+1へ更新すれば元が古くなります。逆方向の更新でも同じです。
  • 切替直前の再取得は、その直後の同時更新を防ぎません。双方向同期にも、複数保存先・メモリを含む同じ問題が残ります。
  • 元側を更新不能にし、更新可能な認証情報の所有権をレーンへ渡すなら、実質的にAになります。
  • 元側だけがrefreshし、レーンにはaccess tokenだけを渡す方法も、Claude Codeがその状態で長時間・表示・feedbackを維持できる根拠がありません。
  • レーン自身で毎回別の正規ログインを行えば複製を避けられますが、ブラウザ承認が必要となりR2を満たしません。
  割り当てはAと同じ8レーンが候補ですが、元フォルダ16個を追加しても並列性は増えません。
  B独立での本番実装は勧めず、正規ログインによる初期登録の手順だけ流用します。
  ## 5. 案C：正規ログインを保ち、通信口座をプロキシで変える
  最小の実証に向きます。表示口座と実際の利用口座の不一致を受け入れる必要があります。
  • ANTHROPIC_AUTH_TOKENを外し、正規ログインとANTHROPIC_BASE_URLだけで起動する条件を試験します。他の認証上書き設定も、移行担当者が値を出さずに確認します。
  • 推論要求は現行のforwardWithRotationとAuthorization差替えを流用できます。
  • /status・/usageはログイン側の口座を示す可能性があります。実通信口座はRotator側で確認し、画面表示を実際の計上先の証明にしません。
  • 表示用ログインが失効すると、プロキシ側に使える口座があっても、Claude Codeが送信前に止まる可能性があります。
  /feedbackの扱い：
  • BASE_URLを通るか、直接送信されるかを先に確かめます。
  • 通る場合、推論以外の対象通信を分類し、feedbackには元の正規ログインのAuthorizationを保持します。口座の自動振替・別口座への再送は行いません。
  • 宛先も実際の経路で確認します。現在の汎用転送へ流すだけでは、feedback対応と判断できません。
  • 成功条件は送信成功表示・受付IDです。zip保存は成功に数えません。
  R8を改善するCの構成：
  新方式の口座は、1口座につき一つの正規ログイン保存先を持ち、更新はその保存先のClaude Codeに任せます。
  プロキシは最新access tokenを読み取り、refresh tokenを別保管庫へ複製せず、refreshも行いません。
  既存のRotator所有口座は移行完了まで従来の所有方式を保ち、同じ系列を新方式と並行更新しません。
  100セッションは16口座へ概ね6〜7ずつを初期目安として、使用量と負荷で調整できます。
  Cでは同じ口座への複数セッション割当は通常の分散です。一口座を複数のrefresh所有先へ割り当てないことを排他対象とします。
  ## 6. 案D：Cから始め、同じレーンのままAへ進む
  C期から将来Aで使う固定dirと接続先を使うことが重要です。
  1. 本番37891を残し、新方式は別ポート・別台帳で起動します。既存のruntime-state.jsonを共有しません。
  2. 最初は1レーン・2口座。旧側14口座、新側2口座のように分け、同じ口座を両方の更新対象にしません。
  3. 旧側からの口座解放は、新規割当・usage起因refresh・進行中refreshが残っていないことを確認してから行います。確認できない口座は移行しません。
  4. 新規セッションは最終A用のレーンdirで、正規ログイン＋BASE_URLだけで起動します。C期はプロキシで振り分けます。
  5. Aの試験後、対象レーンの通信先を現在のログイン口座へ揃え、プロキシをAuthorization保持の素通しへ切り替えます。その後、保存先切替を有効にします。
  6. 新規起動分と旧セッションの自然終了に合わせて8レーンへ拡大します。旧側の容量が不足する場合は拡大を延期します。
  この形ならC→Aでdir・BASE_URLを変える必要を減らせます。
  ただし、旧セッションを無期限に保持するなら旧方式も併存します。既存100セッション全部の表示を即時に変える保証はありません。
