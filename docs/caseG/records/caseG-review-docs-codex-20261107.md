## 4. 設計上の要点
• Aは、予約、受付待機、進行中作業の完了待ち、活動側の最新取得、移動、保存照合、各セッションの追従確認、再開を分ける。管理用の世代番号はサーバーのtoken世代そのものではない。
• Keychain、oauthAccountを持つJSON、各プロセスのメモリを一つの原子的な更新にできるとはしない。書込順や比較後のrenameだけでは非協調ライターとの競合を解決できない。
• 失敗時は最新状態を保全し、不明な外部更新を認めたら古い控えへ自動復元しない。結果不明の対象だけを停止・回復待ちにする。
• Aの初期配置案は8レーン、各12〜13セッション、各レーン専用2口座。4レーン×13と4レーン×12で100セッション、活動8口座・待機8口座とする。
• 97%で次口座を予約し、98%を目安に新しい作業を待機させる。ただし観測遅延・進行中消費を含め、高負荷では前倒しが必要。欠測・古い使用量を0%にしない。
• 口座の所有先・予約先を一元管理し、旧方式と新方式も含めて二重更新を防ぐ。候補がなければ待機する。
• Cは100セッションを16口座へ概ね6〜7ずつを初期目安に分散できる。排他すべきものはセッション数ではなく、同系列のrefresh所有先である。
• Dは本番と別ポート・別台帳で少数から始め、新規セッションを将来の固定レーンdirへ入れる。旧側の口座解放と進行中refreshの完了を確認してから新側へ渡す。
• sessionAffinityのholdはHTTP要求の保持であり、ツールを含むターン全体や背景refreshの停止を証明しない。割当のgenを認証情報の世代として流用しない。
• 通常の実行ファイル、USER、HOME、dir文字列をそろえる。KeychainのACL・確認画面・保存形式の変更は別々に観測する。子・背景セッションの環境継承も試験する。
既存ソースの流用・変更候補は、proxy-server.jsの転送・認証解決、session-affinity.jsの予約・割当、account-manager.jsの使用量・候補選択、secret-store.jsの排他・handoff記録である。
Claude Code所有口座ではnative-claude-refresher.jsによる代理refreshとlive credentialのミラーを併用しない。claude-keychain.jsの名前計算を検証し、claude-credentials.jsの読取を無条件に流用しない。
新方式の設定・起動はconfig.js、install.js、cli.jsへ明示的なモードとして追加する候補とした。ここではコードを変更していない。
## 5. 第2回の補足回答
• CでRotatorがrefreshしない場合、更新担当は口座フォルダを使う正規Claude Codeである。未使用でClaude Codeも動いていない口座は、誰も更新しない。
• 保守用Claude Codeの常駐、定期起動、利用前の短い起動が候補。ただし短い起動だけで必ずrefreshが完了するか、無対話で何を実行すればよいかは未検証。
• claude auth statusだけで更新されるかも未確認。試験3は通常起動による保存更新の後にauth statusを実行しており、更新手段の証拠にはならない。
• 更新周期を12時間と固定しない。認証成功と保存反映の確認方法を試験で決め、同じ口座の保守起動を集約する。
• 起動済みの旧セッションは自然終了まで旧経路を維持し、新規起動分から移す方針とした。旧経路の裏での口座切替は従来どおり継続する。
• 設定からダミーのANTHROPIC_AUTH_TOKENを外すだけで、保持セッションの認証モードが変わるかは未確認。既存セッションのdir変更も前提にしない。
• R3が「API Usage Billingを出さず通常のサブスク表示にする」ならCは候補。表示口座と実通信・計上先の一致まで必要なら、別口座へ振り分けるCはそのままでは不適合。
• D採用とC期の表示ずれ許容は、T3計画に依頼者の回答済み事項として記載されている。再確認事項にはしない。R4の送信成功とR8の成立条件は独立して残る。
