# 案G 修正の計画（2026-11-03）

作成: 2026-11-03（JST）／Grok Bot と Codex の相談結果。設計の中身は `design.md`、試験の手順は `next-tests.md`。

> 状態: **計画の案**。坂根さんの承認前。各段は「実装 → focused test → 二重レビュー → 坂根さんの承認 → 導入」の順で進める。本番の Rotator は最後まで止めない。

## 方向

案D: **C（正規ログイン＋BASE_URL だけ、プロキシが送り先を差し替え）で新しいセッションから移し始め、試験に通ったレーンから A（レーンの認証情報を移して切り替え）へ進める。** 既存のセッションは自然に終わるまで今の方式のまま（裏での切り替えは今どおり）。

## 段の前に行う試験（コード変更なし）

実装の前に、`next-tests.md` の T1（A の短期再現）、T3（C の成り立ち）、T4（休眠口座の保守）を先に行う。特に T3 で「BASE_URL だけでサブスク表示になり、推論が通り、`/feedback` が送れる」ことが確かめられなければ、C を前提にした PR1〜PR3 は組み直す。

## PR の単位と順番（Codex の案に、試験の関門を足したもの）

| 段 | 1つの PR でやること | 入る条件（関門） | 止め方・戻し方 |
|---|---|---|---|
| PR1 | C の通信の分類（推論／feedback などの補助）と認証のモードを、**既定オフ**で追加 | T3 合格 | モードを有効にしなければ今の動作。別ポートの偽の上流で検証 |
| PR2 | 口座ごとの「更新の持ち主」と、アクセストークンを読むだけで渡す仕組み。Claude Code が持つ口座では Rotator は更新しない（`native-claude-refresher.js` を呼ばない） | T4 合格（休眠口座の更新方法が決まる） | 新しい持ち主の移しかえを止める。移した口座の持ち主を自動では戻さない |
| PR3 | 新しい起動用の設定（例: `claude-rotator launch`。口座フォルダ・USER・HOME をそろえて起動）と、旧→新の口座の受け渡し。C を少数（新側2口座）で導入 | PR1・PR2 の導入、T5（計上先）合格 | 新しい導入と再割り当てを止め、最後に確かめた経路を保つ。旧本番は続ける |
| PR4 | A の1レーン・2口座の移しかえ処理と、落ちたときの回復状態 | T1・T2（A の長期）合格、R8 の協調方法の確認 | 既定オフで始める。外からの更新と協調できると確かめられなければ本番に上げない |
| PR5 | レーンの予約、97〜98% の判断、段階的な拡大（最終 8レーン） | T6（サブエージェント）・T7（並行）合格 | レーンごとに切り替えを止める。不明なレーンだけ待たせる |
| PR6 | 旧方式の利用がゼロになったのを確かめてから、不要な旧経路を整理 | 旧セッションが残っていない | C などで要る経路は残す。古い認証情報を戻すことを戻し方にしない |

各 PR: 関係する focused test を先に（例 `npm test -- test/proxy-server.test.js test/session-affinity.test.js`）、PR 前に `npm run check` を1回。macOS/Ubuntu × Node の組み合わせは GitHub Actions を正本にする（`AGENTS.md`）。

## 移行の流れ（本番を止めない）

1. 本番 Rotator（37891）と既存の約100セッションはそのまま。
2. 新方式は別ポート・別台帳で横に立てる。最初は口座を2つだけ新側に移す（旧側14、新側2）。同じ口座を両方が更新しない。
3. 新しく起動するセッションだけを新方式の起動コマンドで立ち上げる。
4. 問題がなければ、旧セッションが自然に終わるのに合わせて口座を新側へ移していく。
5. 旧側が空になったら PR6。
